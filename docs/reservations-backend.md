# Reservation backend contract

This isolated module never calls advertising or transfers tokens. Runtime capabilities default to disabled. PostgreSQL, private Blob, RPC, Channels and AI resource coverage must be verified before enabling them; observed Gateway credits alone are insufficient. Test adapters are injected only by tests.

## UI contract

All paths are relative to `/api/reservations`. Errors are `{code,message}`. Authentication uses `__Host-reservations_session`, Secure, HttpOnly, SameSite=Strict, Path=/, 30 minutes. Challenge expiry is 120 seconds. Origin/RP ID are exact server configuration. Role is `host` only for the configured host address, otherwise `brand`.

`GET /auth/session` and successful verify return `{identity:{ownerId,address,role},expiresAt,pendingAttempt}` (session expiry may be null on restoration). `pendingAttempt` is null or the owner's latest active `{id,operation,offerId,snapshotId,state}`. This durable summary supports reload and device changes without depending on sessionStorage or requesting another signature. Follow its ID with GET reconciliation.

The config also includes effective `intakeEnabled`, `admission`, `accountWasmHash`, `webauthnVerifierAddress` and read capabilities `reading`, `offerReading`, `mediaRead`, `recovery`. Environment flags are ceilings; the live PostgreSQL gate controls new changes, uploads, inference, publications and reservations across warm processes. Auth, private/public reads and reconciliation remain available during a pause if their resources remain covered. Confirmed receipts are read from the database without another transaction call; HTTP still revalidates wallet authority. Logout revokes by cookie hash without wallet RPC, even after expiry; on database failure it expires the browser cookie while explicitly reporting that server revocation could not be confirmed. See [shared admission and recovery operations](reservations-intake.md) for activation order, the CLI, quota isolation, pause boundaries and rollback compatibility.

`mode` is `DISABLED` by default, `CONTROLLED` for admitted test wallets, or `PUBLIC` only after H4 acceptance and observation. `RESERVATIONS_ALLOWED_BRANDS` is a private server-side address allowlist used only in CONTROLLED mode. Config never exposes it. Session/verify `identity.mayReserve` tells the UI whether this wallet may start or submit a new reservation. The server checks admission independently before reservation simulation and again before initial submit. Removing a wallet from the allowlist never blocks its existing receipts or pending reconciliation. Only the explicit configured host can publish in either enabled mode.

CONTROLLED restricts this application's admission and sponsored relay. It is not a contract-level brand allowlist: someone who independently signs and submits directly to the public Testnet contract can still reserve an AVAILABLE offer. This boundary must be considered when running the controlled demonstration; the backend does not claim exclusive control over public chain access.

`GET /config` returns `{enabled,network:"stellar:testnet",origin,rpId,rpcUrl,networkPassphrase,contractId,projectId,capabilities:{authentication,project,media,publication,reservation,conversation},reasons:[{capability,code,message}],limits:{spaces:20,uploadBytes:2097152,imageWidth:2048,imageHeight:2048,conversationPerDay:30,inputTokens:8000,outputTokens:1024}}`. Capability false means the corresponding action must stay unavailable; reason codes include `DISABLED`, `CONFIGURATION_MISSING`, `COVERAGE_UNVERIFIED`, `COVERAGE_EXPIRED`. No provider credentials or resource account details are public.

`GET /project` returns `{project}`. Project is `{id,revision,title,context,spaces:[{id,name,purpose}],map:{mediaId,points:[{spaceId,x,y}]}|null,editorialState:"DRAFT"|"APPROVED",approvedSnapshotId:string|null,conversation:[{id,role:"user"|"assistant",content,createdAt}]}`. IDs are 64 lowercase hex. `PUT /project` accepts **only** `{expectedRevision,title,context,spaces,map}`. Existing space IDs must belong to this project. New spaces omit `id`; the server assigns it. Points refer to existing spaces, so save new spaces before placing their points. `title` is 1–120 characters, context 0–4000, name 1–80, purpose 0–500. All coordinates are finite in [0,1]. Empty initial project title is allowed only before first edit. Editing invalidates current approval and increments revision; old snapshots stay unchanged.

`POST /media` accepts raw PNG/JPEG/WebP, with the matching Content-Type, at most 2 MiB and 2048×2048 decoded pixels. Returns `{media:{id,width,height,mime:"image/png"}}`; no Blob URL. The owner reads `/media/:id`. Published cards reference `/offers/:id/media`, which resolves only the image in that immutable approved snapshot.

`GET /project` additionally includes `approvedSnapshot` (the immutable object, or null) for restoring review. An approved snapshot exposes only the chosen space's map point; the entire referenced image is public after publication and must be shown in the review. The decoder strips metadata and normalizes to PNG; a valid compressed source may be rejected if its normalized PNG exceeds 2 MiB. A durable STAGED media row is created before Blob PUT and becomes READY only after success. Unknown uploads retain their quota and STAGED record; they are never served or approved.

`POST /approval {expectedRevision,spaceId}` returns `{snapshot}`. Snapshot: `{id,projectId,revision,spaceId,title,context,space:{id,name,purpose},map,contentHash,approvedAt}`. `GET /offers` returns `{offers:[{id,snapshot,state,holder,publishedAt}]}`. Card state is `AVAILABLE`, `RESERVED`, `UNAVAILABLE` or `UNCERTAIN`, never inferred from absent/archived chain data. `GET /offers/:id` returns `{offer}` with the same shape. Exclusivity covers one opaque offer; it does not establish physical rights or a time interval.

`POST /conversation {message,expectedRevision}` returns `{message,proposal}`. Proposal is `{summary,title,context,spaces:[{name,purpose}]}`. It is an assistant message requiring explicit user review and PUT; it never edits, approves or publishes. System, schema, current project, selected history and message must fit a conservative 8,000-byte token upper bound. Thirty requests per host per UTC day and 1,024 output tokens are hard limits before the provider.

## Exact transaction handoff

`POST /attempts/prepare` accepts `{operation:"publish",snapshotId}` or `{operation:"reserve",offerId}` and returns:

```json
{"attempt":{"id":"opaque-id","operation":"publish","state":"PREPARED","offerId":"64-hex","snapshotId":"64-hex","actorAddress":"C…","expiresAt":"ISO8601"},"review":{"operation":"publish","offerId":"64-hex","contractId":"C…","title":"Reviewed title","spaceName":"Stage","network":"stellar:testnet","paymentRequired":false},"signing":{"func":"HostFunctionXDR","auth":["unsigned SorobanAuthorizationEntryXDR"],"signerAddress":"C…","expirationLedger":123,"contextRuleIds":[0],"networkPassphrase":"Test SDF Network ; September 2015","rpcUrl":"https://soroban-testnet.stellar.org","contractId":"C…","method":"publish"}}
```

Rule 0 is returned only after validating the wallet's actual single original Default WebAuthn authority. The client signs the provided entry using the existing wallet; it must not rebuild arguments, nonce or expiration. `POST /attempts/:id/submit` accepts **exactly** `{func,auth:[signedEntryXDR]}`. Return is `{attempt,receipt:null|{txHash,ledger,explorerUrl,offer}}`. `GET /attempts/:id` returns the same reconciliation response without signing material. Attempts are owner-only. Repeating prepare returns the prior active attempt, not a new submission. The attempt ID is the idempotency key.

`review` also includes `snapshotId`, `projectId`, `spaceId`, `actorAddress`. Compare these against the reviewed snapshot and decoded function; reserve must bind the selected offer and connected brand. A concurrent prepare may return the same PREPARED attempt with `signing:null` while its creator completes simulation. Recovery must first GET the persisted attempt. A still-PREPARED, unexpired attempt can be reviewed and resumed through the same prepare request; no second intent is created. Editing the project after preparation prevents publication of the old review.

States: `PREPARED`, `SUBMITTING`, `PENDING`, `NEEDS_RECONCILIATION`, `CONFIRMED`, `REJECTED`, `CONFLICT`. Only PREPARED exposes signing. Expired PREPARED with no submit can be rejected. SUBMITTING/unknown cannot be released by time. Persist signed payload before relay, claim one sender atomically, and never resend after uncertainty. Confirmation requires transaction success, an attributable contract event, and matching authoritative contract state. A same-holder read alone is insufficient. Contract archival, missing hash or expired RPC history keeps reconciliation blocked for operator evidence.

Even a FAILED transaction must match the actual envelope hash, operation and complete signed payload before releasing a publication lock. Archive guards inspect both `restorePreamble` and Protocol 23 `archivedSorobanEntries`; an Available simulation value accompanied by restoration metadata remains unavailable. Final RESERVED projections never regress to AVAILABLE when RPC data is stale. Contract `publishedAt` and `reservedAt` are Unix timestamps; receipt `ledger` is the confirmed transaction ledger.

## Resources and operations

`RESERVATIONS_RESOURCE_COVERAGE` is a server-only JSON attestation. It requires a stable `id`, future `verifiedUntil`, `zeroAdditionalSpend:true`, `platformHardCapsVerified:true`, and explicit resource flags under `resources`: `functions`, `transfer`, `database`, `rpc`, `blob`, `channels`, `gateway` as applicable. These are operator assertions backed by release evidence, never inferred from a successful API call. Missing or expired assertions disable that capability.

`quotas` supplies positive integer cumulative allowances scoped to this coverage ID: `functionRequests`, `transferBytes`, `rpcCalls`, `channelsSubmissions`, `blobWriteBytes`, `blobReadBytes`, `gatewayReadCalls`, plus the dedicated `recoveryRequests`, `recoveryTransferBytes`, `rpcAuthCalls`, `rpcRecoveryCalls`. They are atomically consumed before downstream work, shared across server processes, and never refunded after uncertainty. Metered HTTP requests conservatively reserve a full 2 MiB response allowance; the closed config response can still explain recovery when ordinary capacity is unavailable, without reading the gate. Login also reserves 10 requests/IP/minute and 60 requests globally/minute before wallet authority RPC. Anonymous login, publication simulation, relay and public polling cannot use dedicated recovery quotas. Dedicated HTTP capacity requires a locally valid session and the appropriate local resource owner; authority is then verified with the reserved RPC pool. Their exhaustion remains an explicit external recovery block; it never clears attempts. An operator must allocate sufficient recovery capacity and renew verified coverage before expiry.

The Blob SDK's default automatic retries are disabled by the required `VERCEL_BLOB_RETRIES=0`; otherwise media capabilities fail closed. An ambiguous PUT does not perform an unbudgeted fallback GET. Gateway inference is explicitly restricted to the Google provider for the configured Google model, with no alternative provider or model fallback. If that route is unavailable, the request fails and preserves any uncertain cost hold.

AI additionally requires `autoTopupDisabled:true`, `byokDisabled:true`, `exclusiveGatewayBudget:true` and `gatewayBudgetMicrousd`. The shared `gateway_budget_reservations` table is the admission point for every future Gateway consumer, including ads; do not enable another consumer until it uses this same pool. Before inference, reserve 1,210 microUSD and one of thirty host requests/day atomically, GET current credits and model pricing, and check all outstanding holds against current credit. Pricing must match 0.0000001 USD/input token and 0.0000004 USD/output token for the configured model. No tools, search, retries or paid service tier is enabled. Completed calls retain the conservative maximum reservation; usage is recorded without estimating an unverified refund. Timeout or malformed output becomes UNKNOWN and preserves the hold. An observed credit balance alone leaves inference disabled while top-up/BYOK and platform quotas are unverified.

Apply migrations explicitly with `npm run reservations:migrate` after explicitly configuring `RESERVATIONS_DATABASE_URL` against reviewed capacity, schema and role in the **existing PostgreSQL service**. This does not require or provision a new database service. There is no automatic fallback to Ads environment settings. Prefixed reservation/identity tables coexist with the existing application; the shared resource and Gateway budget tables must remain the same accounting pool for future consumers. Startup does not migrate or provision services automatically. Migrations use advisory locks; publication and shared budgets use PostgreSQL transactions and database constraints, not process-local caches.

Existing sessions have their own pre-RPC revalidation guard: 60 requests/IP/minute, 60/wallet/minute and 120 globally/minute. Login challenge/verify retain the separate 10/IP and 60/global limits. Every session request still validates current wallet authority and consumes `rpcAuthCalls`; normal project work and receipt recovery do not exhaust login admission.

Login verification uses three phases: commit the one-use challenge claim in a short transaction, check wallet authority and the real WebAuthn signature without holding a database connection, then acquire the wallet lock in another short transaction to recheck the latest counter and atomically commit identity/session changes. A failed provider call or session write never restores challenge reuse. Concurrent equal counters cannot both create sessions. This avoids nesting the RPC quota transaction inside an open authentication transaction on the same PostgreSQL pool. PGlite tests exercise real P-256 assertions and the same database-backed quota path; native PostgreSQL pool stress remains a separate CI/runtime gate.

## Retention and backup operations

These are operator CLI operations, never public API endpoints or automatic page-load effects. `node server/reservations/operations.mjs cleanup` is a read-only plan by default. The explicit `--apply` claims eligible media as DELETING in a database transaction **before** contacting Blob and consumes `blobDeleteCalls` plus transfer allowance before each deletion. A provider failure leaves DELETING and an audited NEEDS_RECONCILIATION operation. There is no automatic retry; inspect with `cleanup --resume`, then explicitly apply only the reviewed plan. Confirmed deletion becomes DELETED while retaining the audit row and storage key. These commands were tested only with local fake storage; no real deletion has been executed.

The cutoff is thirty days. A current revision linked to any offer is protected, including unresolved or historical attempts. A newer inactive draft with no offer linked to that revision can expire: its private fields and old messages are cleared and its revision advances. Earlier snapshots, offers, attempts, receipts, accounting rows and chain state remain intact. A media object is eligible only when older than the cutoff and unreferenced by **any** remaining project map or immutable snapshot, including snapshots from another project. STAGED orphans are eligible under the same rule. Historical snapshots are retained conservatively even when unpublished, so their referenced images are not considered orphans. Concurrent attachment cannot race the delete claim because project updates require READY media under the same project lock.

Backups use a bounded logical export, with a 64 MiB/10,000-rows-per-table limit. They contain the configured project's immutable IDs and relations, relevant identity counters, sessions/challenges, private image bytes and original Blob keys, and the **entire shared resource/Gateway accounting pool**. They never contain provider credentials or wallet private keys. Artifacts still contain sensitive project data and must be kept in a private encrypted location outside the checkout, public roots and synchronization folders, with owner-only ACLs. File mode 0600 is requested where supported; Windows operators must verify the directory ACLs. Record the returned checksum and source release SHA separately through a trusted channel; a checksum detects corruption, it does not authenticate an untrusted file.

Before export, pause new operations on **every** writer, drain in-flight calls, and freeze any other consumer of the shared Gateway pool. Both RESERVATIONS_ENABLED and RESERVATIONS_INTAKE_ENABLED must be false. The shared admission row must also be paused (or missing, which fails closed); verify that no older binary bypasses it. Current coverage for private reads must remain verified. The source export uses a repeatable-read transaction; image bytes are verified by hash and backup-read counters are included conservatively. Never treat an older backup as proof that no transaction happened after its checkpoint.

```powershell
# Inspect operation arguments; no export or write occurs without --apply.
node server/reservations/operations.mjs backup --file "$env:LOCALAPPDATA\AgenticRealities\Backups\reservations-YYYYMMDD.json"
# Explicitly export to a new file in the pre-created protected directory.
node server/reservations/operations.mjs backup --file "$env:LOCALAPPDATA\AgenticRealities\Backups\reservations-YYYYMMDD.json" --apply
```

Restore only into an **empty migrated schema within existing reviewed PostgreSQL capacity**, with the same Testnet/project/host/contract binding and intake paused. Never overwrite or merge live data. Point the explicit reservation connection at that reviewed target and apply migrations first. Then `restore --file <private-file>` validates and previews counts; `restore --file <private-file> --apply` imports all rows transactionally and returns an operation ID. Corruption, mismatched project or a nonempty target rolls back without a successful import claim. Session hashes remain for audit but are revoked; outstanding login challenges are consumed. PREPARED attempts become NEEDS_RECONCILIATION because a backup cannot establish that they were never submitted afterward. Existing pending/signed intents, confirmed receipts, IDs, costs and relationships are preserved; RESERVED/SENT model holds become UNKNOWN, never refunded.

Imported READY images begin STAGED until their bytes are verified. Run `verify-media --file <private-file> --operation <restore-id>` for a plan and add `--apply` to execute. Each existing Blob is read under quota and compared by hash; only a definite 404 permits a separately budgeted PUT using the original key and backed-up bytes. Ambiguous reads/writes leave STAGED and preserve the operation for explicit recovery. No object is overwritten. The result distinguishes database restoration from media verification and always reports `requiresFreshCoverage:true`. Keep intake disabled until current credits/quotas, restore evidence, pending intents and authoritative chain state are reconciled; restore never authorizes a new signature or transmission by itself.

For larger archives, use native `pg_dump --format=custom --no-owner --no-acl` and `pg_restore --single-transaction --no-owner --no-acl` against a separately reviewed empty schema/database in the existing service. Select all identity/reservation tables, `resource_limits`, `gateway_budget_reservations` and the migration ledger together; preserve the private image archive separately with hashes and original keys. Use a protected PostgreSQL service/password file instead of embedding credentials in shell commands. Perform the same pause, identity invalidation, conservative intent/cost hold, media verification and fresh-coverage gates after native restoration. This path is a runbook; no remote backup/restore has been performed or claimed.

Run `node --test --test-concurrency=1 test/reservations-*.test.mjs`. By default this uses local PGlite with unchanged migrations. Native CI must provide PostgreSQL and set `NODE_ENV=test`, `RESERVATIONS_TEST_DATABASE_URL=postgresql://<test-user>:<test-password>@localhost:5432/reservations_test`. The helper rejects another database, query overrides or non-test mode, creates a random isolated schema, and drops only that checked schema on completion. Never set this variable to production, advertising storage or an existing shared schema.

Deployment integration must route `/api/reservations/*` to `api/reservations.js` (or the platform's equivalent explicit route), preserve raw upload bodies, allow the bounded 90-second relay timeout, and bypass caching. Local servers can adapt Request/Response with `createApi(createRuntime())`. The existing wallet deployment relay remains unchanged and the reservation relay never accepts deployment, wallet mutation, transfer or arbitrary sub-invocations.

Protocol references: [transaction submission and NOT_FOUND](https://developers.stellar.org/docs/build/guides/transactions/submit-transaction-wait), [automatic restoration](https://developers.stellar.org/docs/learn/fundamentals/contract-development/storage/state-archival#contract-data-automatic-restoration), [smart account/passkey integration](https://developers.stellar.org/docs/build/apps/guestbook/setup-passkeys#the-smart-account-client). AI SDK 7 APIs were checked against the installed `ai/docs/03-ai-sdk-core/10-generating-structured-data.mdx` and `@ai-sdk/gateway/src/gateway-fetch-metadata.ts` sources.

## Release gates

PGlite tests exercise the actual migration and SQL constraints. They do not establish native PostgreSQL availability, deployed contract binding, browser passkey behavior, provider credit coverage or real event decoding. No live provider call is made by the test suite. Production factories never fall back to test adapters. The public testnet gate additionally requires those external checks, two-account browser privacy verification and native PostgreSQL concurrency evidence.
